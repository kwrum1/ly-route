# 产品功能验收契约

> 本文只定义“功能批次”的通过标准，不是每次提交的开发门禁。日常修复按[开发、热修复与验收流程](development-workflow.md)执行。

## 功能通过条件

一个功能只有在以下四点同时成立时，才能在功能批次中标记为通过：

1. 管理员从真实 UI 填写或修改配置；
2. 后端收到并持久化最终配置，回读内容与 UI 一致；
3. VPP 或相关服务应用了配置，运行态可查询；
4. 独立客户端用真实报文观察到预期结果。

不要求每个小修复都重装 ISO 或重跑全部功能。修复只需重跑原场景和受影响的核心冒烟；功能批次收口时再执行完整范围。

## 结果分类

| 结果 | 含义 | 处理 |
| --- | --- | --- |
| `PASS` | 产品行为已被四点证据证明 | 记录证据 |
| `PRODUCT_FAIL` | 首个失败层位于产品代码或配置生成链 | 修复源码并热部署 |
| `FIXTURE_FAIL` | 测试服务器、客户端、代理节点或网络拓扑失败 | 修复夹具，不改产品 |
| `BLOCKED` | 缺少外部资源或权限 | 登记原因，不重复空跑 |

## Gateway 批次范围

按产品功能边界覆盖：管理口与网卡角色、PPPoE、LAN/DHCP、IPv4/全锥 NAT、端口映射、多 WAN 群组、策略路由、DNS 透明接管与 DNS 分流、代理 WAN、GeoIP/GeoSite、IPv6 PD/RA、限速、智能 QoS、安全控制、监控、配置和升级。

## Orchestrator 批次范围

只覆盖编排器自身：逻辑进/出接口、编排组、组顺序、策略明细 CRUD、any/IP/CIDR/范围/IP 组/端口/协议匹配、指定编排路径、限速、安全边界、节点故障 bypass 和运行态统计。

编排器不重复验收 Gateway 的 NAT、DHCP、DNS、PPPoE 或代理服务。

## 批次执行规则

- 一次批量收集互不依赖的场景，先登记全部失败，再集中修复。
- 默认保留现有环境、日志和客户端；只有拓扑确实改变时才建立新基线。
- 功能修复优先替换受影响的二进制或插件；rootfs/ISO 只在批次通过后固化。
- 性能、64 字节小包、温度、ESXi VMXNET3/VFIO 和物理 PCI 所有权不属于普通功能批次，必须另开硬件任务。
