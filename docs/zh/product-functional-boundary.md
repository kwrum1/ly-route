# 产品功能边界

本文档是 LY-Route 的规范性范围契约。实现状态和实施顺序分别见[实现状态盘点](implementation-status.md)与[工作计划](work-plan.md)。

## 共同规则

- Gateway 与 Orchestrator 是两个构建期确定的产品，分别拥有产物、profile、数据库、迁移、API 白名单、UI 路由、服务和升级流程。
- 禁止运行时产品互转和跨产品配置导入。
- 可以共享基础代码，但产品能力测试必须证明产物中不存在越界服务、API、资源、页面或迁移。
- 共享选择器自动探测已分配网卡，优先选择实测通过的最优 VPP 原生高性能候选；没有原生候选通过时才使用 VPP DPDK。每台设备的全部活动数据接口必须统一采用其最高共同合格等级，Gateway 和 Orchestrator 都不得按端口或编排组混用等级。两个等级都失败时数据面锁定，管理面保持可访问。
- AF_XDP copy、Linux 通用 XDP 转发、内核转发及其他兼容性降级路径不在生产候选范围。AF_PACKET 仅允许在明确启用 `LY_ROUTE_VMXNET3_AF_PACKET_ACCEPTANCE=true` 且网卡驱动为 `vmxnet3` 的 ESXi 功能验收环境中使用；它不是 PCI 独占或高性能生产路径。

## 出口网关 Gateway

Gateway 是路由型 LAN/WAN 出口设备。

范围包括：接口与 WAN 组、路由、NAT、DNS、DHCP、代理、PPPoE、流量策略/QoS、安全策略、遥测、运行时诊断、备份恢复、升级和维护。

- WAN 组首版只支持主备、加权负载和五元组负载；代理逻辑 WAN 不得加入任何 WAN 组。
- Gateway 对 LAN 终端发出的全部 IPv4/IPv6 TCP/UDP 53 流量执行透明劫持，不依赖终端是否通过 DHCP 获得 DNS。即使终端手工配置 `223.5.5.5` 或其他任意 DNS 目标，查询也必须进入网关 DNS 引擎，并由实际命中的 DNS 策略决定真实上游和出口线路。DNS 是独立的有序首匹配引擎，可选择固定 WAN/上游/代理、固定应答或 NODATA；其选线优先于普通策略路由。DNS 应答产生的目标 IP 在 TTL 有效期内继承 DNS 所选线路。未匹配规则或已匹配线路不可用时返回 NODATA，不回落到终端原目标、默认上游、低优先级规则或普通路由。
- 代理线路只允许绑定一个订阅，不支持把多个代理 WAN 组成 WAN 群组。订阅可选择一个或多个候选节点；“自动选择线路”只使用健康节点中延迟最低的一条，并具备失效切换和恢复机制。
- 订阅的“延迟权重负载”先按 Xray Observatory 的真实代理 HTTPing RTT 排序并取 Top N（默认 Top 2，可选 Top 2 或 Top 3），再按 `1 / RTT` 归一化为整数权重。新建 TCP/UDP 流按源 IP、目的 IP、协议、源端口和目的端口执行稳定的加权五元组 Hash；既有连接不得因重新探测迁移。失效节点立即退出候选集，仅剩一个健康节点时独占 100% 权重；全部节点失效时保留最后有效捕获规则并记录降级状态，避免把正在使用的代理流量突然放行。
- Xray 只提供每个订阅节点的独立 outbound、健康探测和实际代理传输，不使用 Xray `leastPing` 或 `leastLoad` 直接分配业务流量；Top N、RTT 权重、故障摘除及五元组选择由 Ly Route 控制面生成，并仅原子更新代理专用 nftables 表。
- 专用代理虚拟接口默认全代理。直连或代理、国内或外网的策略判断只由 VPP 负责；Xray 只传输已经被 VPP 选入代理路径的流量，不得重复实现业务分流或 DNS 策略。Linux nftables 仅用于把该专用服务接口的流量交付给 Xray。
- QoS 包含两层独立能力：用户可配置的策略限速，以及内部集成、不给用户暴露底层算法参数的智能 QoS。智能 QoS 以 CAKE/SQM 类似的公平排队、主动队列管理和满载低时延体验为目标，但实现必须与选定的 VPP 高性能路径兼容。

每个配置入口必须独立持久化、事务下发，并显示实际运行状态。

## 流量编排器 Orchestrator

Orchestrator 是透明双臂流量编排设备。它只负责决定流量是否以及按什么顺序经过编排组；NAT、DNS、DHCP、PPPoE、WAN 组、端口映射和代理均不属于其职责。

- 基础配置必须先确定且仅确定一个逻辑 WAN 和一个逻辑 LAN。两者都可以由一个物理口或一个聚合组承载；只有二者均有效后才允许创建编排组。
- 默认物理方向为流量从 WAN 进入设备、最终从 LAN 离开；反向连接必须保持对称状态。
- 每个编排组严格包含两个不同且未占用的物理数据接口：一个 `lan_facing`（接 LAN），一个 `wan_facing`（接 WAN），名称可自定义；编排组不允许 bond、bridge 或两个同向端口。
- 逻辑接口及其底层物理成员不得跨组重叠复用；同一物理口不得同时属于两个逻辑端点。
- 流量编排由可拖动排序的策略组和组内有序策略组成：组位置决定组优先级，组内较小序号优先；一条规则未命中则继续下一条，组内未命中则继续下一个组。
- 策略条件首版使用源 IP、目的 IP、协议和端口等 IP 层条件，地址支持 `any`、单 IP、CIDR、连续范围和 IP 组引用。策略动作最终产生 `via`、`direct` 或 `drop`；`via` 可选择一个或多个有序编排组。
- 遍历全部策略组仍未命中的流量默认直接转发至 LAN，不经过任何编排组。
- 安全拒绝先于流量控制，流量控制先于服务链选择。
- `via` 正向流量按顺序经过服务实例，返回流量必须经过同一组实例并严格逆序。
- 服务节点失效时默认 bypass：从有效链中原子移除失效节点，剩余节点保持正向有序和回程严格逆序；无健康节点时等价于 `direct`。恢复必须经健康门禁后再加入，禁止半配置。
- 全部活动数据逻辑接口、bond 成员和对称服务链都通过自动数据面门禁后才能开放转发；整台设备必须采用最高共同合格等级，禁止按端口或编排组混用等级。

## 配置边界

- 策略地址条件使用显式类型化的 `any`、主机、CIDR、范围和稳定对象引用。
- Gateway 支持 IP 组，并仅在策略/运行时确有域名语义时支持域名组。
- Orchestrator 支持 IP 组，但不支持域名组。
- WAN/LAN 接口地址是主机前缀，不是策略选择器；DHCP 池使用范围；NAT 转换端点遵守对应资源的单地址/接口约束。

### NAT 行为边界

- Gateway 默认使用 VPP NAT44-ED（端点相关）行为；未填写 NAT 行为时不得隐式切换模式。
- 需要全锥 NAT 时，在 NAT 相关配置中显式选择 `full_cone`，运行时统一使用 VPP NAT44-EI（端点无关）插件。
- NAT44-ED 与 NAT44-EI 是整台 Gateway 的互斥运行模式，静态映射、端口映射、动态 PPPoE 出口和回程保护必须使用同一模式；检测到混用配置时拒绝应用并保持上一份运行配置。
- 全锥 NAT 的验收必须同时检查 VPP 的 EI 接口/地址/映射回读，并由独立 LAN 客户端发起真实 UDP 会话验证；只看到配置文件或 API 成功不算通过。

Orchestrator 明确保留：流量概况（统计编排组流量）、系统概况、在线用户、Top 连接、网卡设置、编排设置、流量编排、流量控制、安全控制、IP 管理、系统用户管理和配置管理。

Orchestrator 明确排除：WAN 群组、路由/NAT、端口映射、DNS 管控、DHCP 服务、域名管理、Top Domains、代理网关、OAF/DPI/应用识别/上网行为审计、Bridge 模式、云管理、HA 和 VRRP。

## 发布边界

两个产品必须分别提供 x86_64 与 ARM64 产物，并通过全新安装、升级、回滚、产品隔离、API 契约、浏览器、真实包流和故障注入门禁。功能验收按[双产品全功能验收设计](container-network-validation.md)执行；Gateway 必须覆盖 DNS/DHCP、路由/NAT、WAN、PPPoE、代理、QoS、安全、遥测和运维，Orchestrator 必须覆盖完整策略、逻辑端点、双向服务链及节点失效 bypass。只有 schema、路由、mock 或页面不等于功能已交付；软件全功能验收通过后仍需目标硬件性能与驱动门禁才能发布。
# Xray 节点域名解析边界

- Xray 节点地址填写域名时，控制面必须先解析为 IP，再生成 Xray 运行配置；TLS、Reality 的 SNI 保留原域名。
- 节点域名只能使用系统内置 DoH 的固定 Bootstrap DNS：`1.1.1.1`、`1.0.0.1`、`8.8.8.8`、`8.8.4.4`、`9.9.9.9`。
- 控制面按固定列表逐个尝试，首个服务器不可达时继续下一个；全部不可达则拒绝生成该 Xray 运行配置，禁止回落到系统 DNS。
- 不读取 `/etc/resolv.conf`，不继承终端 DNS、DNS 策略或用户填写的普通 DNS，也不允许环境变量覆盖。
- Bootstrap DNS 只负责节点域名的首次控制面解析；用户配置的 DoH 仍是业务 DNS 上游，两者不能混用。
