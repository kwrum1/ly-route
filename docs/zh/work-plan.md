# LY-Route 双产品后续工作计划

> 本文是功能 backlog 和产品范围记录，不是日常开发门禁。实施顺序、热修复和最小验收以[开发、热修复与验收流程](development-workflow.md)为准；未完成的工作包不应阻塞无关修复。

## 1. 计划目标

本计划以当前可验证代码基线和既有产品设计为准，完成两个不可运行时互转的产品：

- **出口网关（Gateway）**：面向 LAN/WAN 的路由出口设备，提供路由、NAT、DNS/DHCP、代理、流量治理、安全与运维能力。
- **流量编排器（Orchestrator）**：带独占或共享 LAN 管理地址的透明流量编排设备。逻辑 LAN/WAN 可使用物理口或 bond；每个编排组固定使用两个未占用物理口，一个接 LAN、一个接 WAN，不允许 bond；按有序策略将正向流量送入服务链，并保证返回流量严格按相反顺序经过同一服务链。

两种产品分别构建、安装、配置、升级和验收。数据面按“**VPP 原生高性能路径优先，VPP DPDK 高性能回退**”自动选择，并在每台设备的全部活动数据接口上采用最高共同合格等级。原生和 DPDK 都必须通过运行时接入、真实流量、性能、开销及回滚门禁；AF_XDP copy、Linux generic XDP、AF_PACKET 和 Linux 转发不用于兼容性降级。所有高性能候选都不合格时，管理面必须可访问，数据面保持锁定并给出明确诊断。

## 3. 实施原则

1. UI 优化采用严格页面验收制：从双产品登录页开始，产品经理提出什么就定向修改什么；当前页面在完整容器中明确验收后才进入下一页面。全部显示与交互验收后，再基于 VPP、后端和 API 探索功能拓展。详细流程见[双产品 UI 优化与功能拓展计划](ui-rearchitecture-plan.md)。
2. 页面不得把内存草稿或静态占位显示成设备真实状态。
3. 所有数据面变更必须具备预检、原子应用、回滚、启动对账和故障可诊断性。
4. 单元测试不能替代真实包流、故障注入和设备产物验收。
5. 每项任务必须提交代码、自动化测试和证据；文档中的“完成”只由证据决定。
6. 两产品采用同一套项目自有 UI 设计系统。现有页面只作为 API、字段和历史问题参考，不再冻结其布局；逐页确认后的信息结构和操作路径才是实装基线。视觉只参考 iKuai 4.0 的浅蓝白和白色主内容面，不复制第三方商标、图标、代码、图片或逐像素布局。
7. 配置语义参考 Panabit 的成熟对象与策略交互，但 API、模型和实现必须项目自有并符合两个产品的能力边界。
8. 功能完成必须按[双产品全功能验收设计](container-network-validation.md)通过契约、容器真实协议/包流、浏览器和系统产物矩阵；物理硬件暂缺不允许用 mock 代替 DNS/DHCP、PPPoE、路由/NAT、代理、QoS 或服务链。性能使用容器化 PPPoE 基准持续回归，真机实验不作为当前发布门禁。

### D1：自动网卡探测与最优数据面选择（P0）

目标：两个产品使用同一选择器，在不牺牲性能和数据面安全的前提下自动选择网卡接入方式。

- 从显式数据端口集合中永久排除 Linux 管理口；采集 PCI ID、驱动、固件、链路、NUMA、队列/RSS、IOMMU/VFIO、hugepage 和 VPP 插件能力。
- 对每张数据网卡枚举 VPP 原生候选，首批包括 RDMA DV 与 VPP AF_XDP zero-copy；执行无残留 attach/detach、最小双向包流和短时性能探测。
- 在通过门禁的原生候选中，按包速率、时延、丢包、CPU/核占用、内存和 NUMA 代价评分选优；禁止只按 PCI ID 或固定顺序认定最优。
- 原生候选全部失败后才探测 VPP DPDK。实现受控解绑/绑定、VFIO/IOMMU、hugepage、队列/RSS、NUMA、VPP 启动、真实包流和失败恢复。
- 保存每端口候选、评分、拒绝原因、最终选择、证明有效期和环境指纹；重启、固件/驱动变化、网卡更换或拓扑变化后重新探测。
- AF_XDP copy、Linux generic XDP、AF_PACKET、内核 IP 转发永不进入候选集。
- 汇总全部活动数据接口（含 bond 成员）的候选结果，选择整台设备的最高共同合格等级。Gateway 不得按 WAN/端口混用等级，Orchestrator 不得按组/端口混用等级；共同等级变化必须整机事务化切换，任一必要接口失败且无共同等级时锁定数据面。

当前进度：共同等级选择、原生优先、DPDK/VFIO 事务接管、启动回读、失败回滚和制品依赖已实现；AF_XDP/RDMA 原生附件已从占位命令切换为 stock VPP 25.10 CLI，控制服务与制品执行器统一 `?` 幂等语义、硬件/netdev 回读和真实删除回滚，容器 veth 零拷贝不合格时验证锁定且无残留。验收要求容器中证明选优、管理口不被接管、证明过期后锁定，并由 UI/API 解释每次选择；真机性能门禁已移出当前范围。

### G1：Gateway 真实数据面闭环（P0）

目标：证明出口网关不是仅有控制面和页面。

- 建立 Linux 容器、网络命名空间、veth、bridge 与 macvlan/等价二层网络组成的可重复拓扑，并建立“功能—需求—场景—断言—证据”覆盖清单，逐项覆盖 Gateway 全部资源而不是只测主路径。
- 实现并验证 DNS 权威优先级：透明接管 LAN 终端发往任意 IPv4/IPv6 目标的 TCP/UDP 53，包括手工配置 `223.5.5.5` 等外部 DNS 的终端；DNS 有序首匹配；支持固定 WAN/上游/代理、固定应答和 NODATA；实际查询上游和出口只由 DNS 策略决定，查询及 TTL 内关联业务流的选线优先于普通 PBR；未命中或命中线路失效不回落到终端原目标。
- 完整验证 DHCP/Kea 多子网、地址池、选项、静态绑定、租约/在线用户、续租/释放、池耗尽、冲突和服务重启，并证明客户端改用外部 DNS 后仍被 53 接管。
- 完整验证策略顺序、类型化地址/对象、路由/NAT44/端口映射、接口/Bond、静态/DHCP WAN、对象、安全、遥测、运行时事务和配置恢复。
- 启动独立 PPPoE 服务器容器，使被测 Gateway/路由器容器通过隔离二层网络真实发现、认证、拨号、获取地址和断线重拨；不得用直接注入“已拨号”状态代替。
- 分别在原生路径和 DPDK 回退路径验证相同 Gateway 语义，并验证路径切换前后的事务与回读。
- 验证配置应用、真实状态回读、重启恢复、失败回滚和管理面存活。
- 为 WAN 组故障、链路切换、DNS/代理不可用和配置错误增加故障注入。

当前进度：DNS 正向和负向发布契约已闭环。API、编译器、SmartDNS 渲染和运行计划统一要求直连解析必须且只能显式选择一个上游或 WAN；未命中、选中解析器不可用以及全部策略禁用均返回 NODATA，不回落到终端原目标或低优先级规则。隐式上游、`continue_rules`、通用 route/NAT 字段及 DoH/DPI 声明会被拒绝，保持零策略写入并生成失败审计；对应两条独立门禁已纳入统一运行器。剩余工作是 SmartDNS 服务重启/漂移、全功能组合故障、UI 和目标硬件证据。

Gateway 网络生产事务、真实 VPP 双向包流和故障门禁也已闭环：接口与 active-backup Bond 经同一生产多资源事务应用和语义回读；部分 Bond generation 失败会恢复原状态；WAN admin-state 漂移由可信完整读回触发修复，读回不完整仍锁定；事务回滚和 WAN 故障期间共享 LAN 管理地址持续可访问。容器 AF_PACKET/veth peer carrier 的自动恢复不作为原生网卡结论，driver/carrier 热插拔仍由目标硬件门禁承担。

Gateway 服务运行与故障门禁已闭环：Kea 真实租约采集接入主程序，按 memfile 最后记录过滤释放/过期租约并在 API 中脱敏，租约库丢失时不返回缓存；PPPoE 生命周期 API 真实控制逐 WAN Ly Route 原生 PPPoE 客户端，等待 IPCP/IPv6CP 收敛，完成 Connect/Disconnect/Reconnect、接入集中器失效和恢复且不保留陈旧接口或路由交接；当前业务数据由 VPP PPPoE 会话承载，拨号控制帧仍通过专用 TAP/AF_PACKET 控制通道，不应描述为“完全无 Linux 控制面”。Xray 最快订阅启用仅回环 RoutingService，正式二进制接受生成配置，产品 API 可读回当前选中节点，在全节点失效时降级并在节点恢复后重新给出实时选择。安全资源现已使用严格 L2-L4 契约，ACL、IP-MAC、IP/CIDR 威胁名单与基础攻击阈值拥有类型化输入，DPI、应用识别、域名/URL/SNI、IDS/IPS 和用户行为声明会被拒绝并审计且不产生写入；聚合 VPP 安全代际已证明合法绑定流量放行、MAC 欺骗与威胁 IP 阻断、错误更新保留有效规则并生成运行时失败审计。真实 PPPoE 容器性能基准已覆盖 NAT44、纯路由和 64B 小包。统一真实验收现为 `33/33`，发布矩阵为 `39/45`。

验收：Gateway 全功能清单不存在未映射设计、跳过项或只有 mock 的必测项；测试记录包含拓扑、构建版本、请求、包捕获、DNS/DHCP/PPPoE/代理日志、计数器、故障和恢复结果；软件层完整矩阵可在 CI 重复执行。

### G2：Gateway 出口策略、代理与双层 QoS（P0）

- WAN 组只实现并验收主备、加权负载和五元组负载；定义健康门禁、主链路恢复、连接粘滞和成员变化行为；在模型、API、导入和 UI 层禁止代理逻辑 WAN 成为成员。
- 代理订阅出口在策略路由中支持 `fixed_node` 与 `fastest_node`。固定节点引用稳定 ID；最快节点先验证代理协议实际可用，再以滚动 ping 延迟为主要排名，加入切换容差、最短驻留、连续失败/恢复阈值和明确切换原因。
- 节点失效时新连接自动切到健康节点；默认不强制中断仍健康的既有连接。ICMP 不可用不等于代理不可用，但 UI/API 必须明确延迟指标不可用并依赖协议健康门禁。
- 提供两个相互独立的 QoS：用户可配置的策略限速，以及内部不可调参数的智能 QoS。后者实现 CAKE/SQM 类整形、公平排队、按流/主机隔离和 AQM 效果，但不得绕过 VPP 或降级到普通 Linux 转发。
- 用并发下载/上传把链路跑满，同时注入 ping、DNS、短连接、语音/交互类流量；记录空载/满载 RTT、抖动、丢包、吞吐、公平性、CPU 和内存，证明智能 QoS 在合理吞吐损失内抑制 bufferbloat。

当前进度：用户 VPP policer 和自研生产级 VPP Smart QoS 插件均已完成运行激活、精确回读和真实包流；2 worker 双向饱和测试已证明整形、主机公平和低满载时延。剩余工作是异常回滚、重启、长稳、多速率/多 worker、UI 运行证据和目标硬件矩阵。Smart QoS 与网卡选择的原生/DPDK 等级相互独立。

验收：三种 WAN 组在容器多 WAN 拓扑中通过成员故障/恢复；固定代理、最快代理、失效切换和防抖通过；策略限速精确可读回；智能 QoS 在双向满载下保持交互体验且高性能数据面未被绕过。

### O1：Orchestrator 后端主链路接线（P0）

目标：把现有独立模块接入产品主进程，形成可用系统。

- 将拓扑、编排组、策略编译、服务链和遥测接入 Orchestrator API 与独立持久化。
- 强制逻辑 LAN/WAN 唯一且可使用物理口或 bond；编排组只能使用两个不同物理口，分别接 LAN/WAN，不允许 bond 或 bridge，且所有底层成员不得重叠复用。
- 拒绝在 LAN/WAN 尚未完整配置时创建编排组；默认方向为 WAN 入、LAN 出，遍历全部策略仍未命中时直接转发到 LAN。
- 拓扑提交必须自动生成唯一 LAN/WAN 之间的基础透明转发候选、应用事务和语义读回，不允许依赖管理员手工执行 VPP 命令或填写页面中不存在的接口地址/下一跳。
- 编排组采用零额外参数的数据面模型：产品只从两个方向端口和组名派生转发，不向用户暴露服务节点 L3 下一跳；若底层实现需要内部标识，必须由系统确定性生成并持久化。
- 定义并实现 `via`、`direct`、`drop` 行为，以及正向链与精确反向链映射。
- 统一 OpenAPI、错误模型、修订号、幂等性和并发冲突处理。

验收：重启后配置与运行态一致；非法拓扑无法落库或下发；API 集成测试覆盖 CRUD、冲突和回读。

当前进度：物理口和 LAN/WAN bond 的零隐藏参数透明数据面已接入生产 API；拓扑/组/策略写入均先写入 `0600` 原子意图日志，再应用 VPP 候选并语义读回，数据库提交后才持久化清除日志；持久化失败会恢复旧候选且回滚失败不再静默。bond 自动创建、差异变更、读回、失败回滚、重启复用、成员故障切换、删除清理，以及模拟崩溃后从日志和数据库对账恢复均有真实证据。旧逐流 service-chain API 和 reconciler 已从透明生产运行时移除。剩余软件 P0 转为应用层节点健康、自动漂移处置和更广协议/压力矩阵。

### O2：事务、健康与故障语义（P0）

- 实现“预检→生成候选→应用→校验→提交/回滚”事务协调器。
- 实现服务节点健康、链路故障和进程重启状态机；节点失效默认 bypass，原子移除失效节点并保持剩余链严格对称，无健康节点时按 `direct` 处理。
- 恢复节点连续通过协议健康和双向包流门禁后才重新加入，防止健康抖动造成频繁改链。
- 启动时对账期望状态与 VPP 实际状态；漂移时阻断增量变更并提供修复动作。
- 让遥测暴露端口、组、规则、服务链、丢弃原因、事务和健康状态。

验收：故障注入测试证明不产生半配置；失败可回滚；重启可恢复；告警包含可操作原因。

当前进度：VPP 插件采用 candidate/commit，Go API 采用原子意图日志→应用→语义读回→持久化→日志提交/失败恢复；重启重放、崩溃日志恢复、bond 生命周期和删除锁定已由真实产品二进制验证。编排组任一方向链路 down 时按包 bypass，恢复后重新入链，计数进入 API/UI。系统概况实时比对 VPP generation，漂移会从 running 转为 degraded，整套策略重放后恢复新鲜收据。仍需自动漂移修复/锁定策略、可选二层节点心跳及连续失败/恢复防抖；没有管理地址时不得宣称能够可靠判断服务应用进程存活。

### O3：Orchestrator 策略与管理 API（P0）

- 实现拓扑、编排组、策略组、有序规则、服务节点/链、运行态和遥测的完整 CRUD/查询接口。
- 安全拒绝优先于流量控制，流量控制优先于服务链选择。
- 明确策略命中、默认行为、优先级移动、引用保护和删除语义：策略组按可拖动位置从上到下，组内按较小序号优先，未命中继续下一条/下一组；支持安全组高于缺省组的典型配置。
- `PUT /orchestrator/policy` 必须形成“校验→展开 IP 对象/范围→生成整套数据面候选→原子应用→语义读回→提交或回滚”的闭环；禁止只保存策略、再依靠逐流 `/service-chain/apply` 才生效。
- 宽匹配规则必须直接覆盖 `any`、主机、CIDR、连续范围和 IP 组展开后的真实流量；不得预先枚举在线连接，也不得要求调用方提交具体五元组。
- 策略组顺序和组内首条命中语义必须在 VPP 数据面可证明；多组命中时按组顺序组成服务链，完整未命中时走基础直达路径。

验收：契约测试与 OpenAPI 一致；同一配置可重复提交；规则顺序和链路方向均有自动化证明。

当前进度：整套策略会确定性展开 IPv4/IPv6、`any`、CIDR、连续范围和 IP 组，最多 4096 个 VPP 规则变体；组位置和规则序号在 worker 数据面执行，`via/direct/drop`、默认直达、双组顺序串联/严格反向和语义回读已通过。待补更多端口协议、IPv6 扩展头与分片安全矩阵、幂等并发压力和 OpenAPI 收口。

### O4：Orchestrator 完整 UI 与菜单校正（P1）

- 首页保持流量概况、系统概况、在线用户和 Top 连接的位置；流量概况改为统计 WAN/LAN 边界和编排组流量，删除 Top 域名。
- 目标菜单固定为：流量概况、系统概况、在线用户、Top 连接、网卡设置、编排设置、流量编排、流量控制、安全控制、IP 管理、系统用户管理、配置管理。
- 网卡设置负责唯一 LAN/WAN 及其物理口/聚合组；编排设置位于网卡设置之后、流量编排之前，只允许从剩余端口选择两个物理口并指定接 LAN/接 WAN方向和名称。
- 将旧“LAN/WAN”改为“编排设置”，将旧“路由/NAT”改为“流量编排”；删除 WAN 群组、端口映射、DNS 管控、DHCP 服务和域名管理。
- 流量编排页面提供策略组创建、拖动排序和组内策略明细；源/目的地址支持 `any`、单 IP、CIDR、连续范围和 IP 组，路径可选择一个或多个编排组，完整未命中时明确显示“直达 LAN”。
- 每个页面使用 Orchestrator 专属 API 和数据库，不复用 Gateway 的 NAT、DNS/DHCP、代理或域名对象。
- 在线用户仅使用 VPP 邻居观测，Top 连接仅使用 VPP 会话/连接观测，禁止复用 DHCP 租约、DNS 域名或 NAT 会话。
- 页面保存成功必须以生产事务提交和 VPP 语义读回成功为准；仅 API 持久化成功不得显示“已生效”。
- 完成保存、预检差异、应用进度、回滚结果、漂移和故障提示。
- 继续完善已接入的编排器类型化限速策略、ACL、仅 IP 地址组和系统用户管理；补齐 IP 组引用、事务失败回滚、重启恢复与组合包流证据，不得引入 Gateway NAT/DNS/域名语义。

验收：菜单和路由无 Gateway 越界能力；三视口 Playwright 覆盖核心操作；页面状态来自真实回读。

### O5：Orchestrator 真实包流与故障 E2E（P0）

- 用容器、网络命名空间、veth、bridge 与 macvlan/等价二层网络建立双臂拓扑和可观测服务节点，验证 `direct`、`drop`、单节点和多节点 `via`。
- 同时建立物理口和 bond 的逻辑 LAN/WAN 场景，并建立严格两物理口编排组场景，验证成员约束、链路故障和恢复；编排组不得使用 bond。
- 在整机原生共同等级和 DPDK 回退共同等级分别验证编排组启用、锁定、重探测与对称链行为。
- 用包捕获和节点日志证明返回流量严格逆序经过服务链。
- 从 UI/API 只提交拓扑和整套策略，禁止测试辅助代码再调用逐流应用接口或注入隐藏下一跳；随后用未预告五元组证明 `any`、CIDR、范围、IP 组、组顺序、规则序号和默认直达均在 VPP 生效。
- 增加 VPP 原生 Top 连接和策略命中观测，验证五元组、字节/包数、命中规则、经过编排组、空闲老化、多 worker 聚合和资源上限；不可观测时必须明确不可用，不得用接口流量冒充规则命中。
- 注入节点失联、端口 down、bond 成员变化、VPP 重启、应用失败和配置漂移，证明默认 bypass 不形成单向链或半配置。

验收：每个场景同时验证包路径、计数器、API 状态、告警及恢复；核心容器矩阵进入 CI，全部通过前不得宣布功能验收合格。

当前进度：双 worker VPP 容器已从产品 API 只提交拓扑与整套策略，验证默认直达不经过服务桥、单组/双组 `via`、严格反向、`drop`、IPv4、IPv6、VLAN 100、链路 down bypass/恢复、产品 API 自动建立 bond、成员故障切换/恢复、规则计数、Top 连接、完整遥测、运行态漂移 degraded/recovery、启动重放、原子意图日志崩溃恢复、bond 清理和删除锁定；同一插件已构建为正式 amd64 deb。待补 DPDK 回退、IPv6 扩展头/分片、容量/长稳、真实进程 kill/断电和目标硬件。

### C1：类型化配置表达与对象引用（P0）

目标：以[配置表达模型](configuration-model.md)替代含义模糊的自由文本配置。

- 为地址匹配实现显式 `any`、单 IP、CIDR、连续起止范围、IP 组引用，以及 Gateway 语义允许处的域名组引用。
- 为端口实现 `any`、单端口、连续范围和端口/服务组；接口、出口和时间计划使用稳定引用。
- 完善 IP/域名组的规范化、批量导入、逐行错误、嵌套/循环检测、展开预览、引用追踪和删除保护。
- 在策略组层支持公共条件，组内规则继承并做细分，顺序、移动和冲突预览可验证。
- 统一 OpenAPI、持久化、导入导出、编译器和审计结构；迁移旧 `src_ip/dst_ip`、空字符串 `any` 和对象名称字符串。
- 保持边界：接口自身地址不能使用 `any`/组/范围；Orchestrator 不引入域名组。

验收：API 合法/非法契约完整；对象重命名不破坏引用；范围确定性编译；删除被引用对象返回消费者；旧值无法无歧义迁移时要求人工确认；真实 VPP 预览/回读与 UI 语义一致。

### C2：成熟配置控件与表单闭环（P1）

- 在现有字段位置把自由文本升级为类型化选择器，不移动页面内容和操作路径。
- 地址控件支持 `any`、主机、CIDR（如 `192.168.1.0/24`）、范围（如 `192.168.1.10-192.168.1.20`）、IP 组和适用的域名组。
- 提供对象搜索、已有对象引用、相邻快捷创建、格式即时校验、规范化/展开预览和使用情况。
- WAN 创建保留当前字段位置，仅优化分区、对齐、掩码输入、错误提示和操作区；WAN 接口地址不错误暴露策略对象选择。
- 路由、安全、流控、DNS、NAT/端口映射和 Orchestrator 策略按适用矩阵接入统一控件。

验收：Playwright 覆盖每种表达、对象复用、坏输入、悬空引用、引用保护、保存/应用/回读；前端不能接受后端无法执行的值，也不能要求用户手填内部对象 ID。

### U1：双产品同步显示与交互优化（P0）

目标：不改变产品功能和 API，从 Gateway/Orchestrator 登录页开始逐页执行“现状 QA、产品需求、定向修改、双容器验证、产品验收”，详细流程见[双产品 UI 优化与功能拓展计划](ui-rearchitecture-plan.md)。

- 只参考 iKuai 4.0 的浅蓝白配色、白色主内容区、轻边框/阴影、蓝色主操作和现代控件质感。
- 建立颜色、字体、字号、间距、圆角、阴影、图标、图表、表格、表单、抽屉、弹窗、状态徽标、空态、错误态和加载态 token。
- 每次只修改产品经理当前指定页面和明确提出的内容；通用样式若影响其他页面必须提前说明，不得连带重构。
- 当前页面未明确验收前不进入下一页面；自动测试通过不能替代产品经理容器验收。
- 每页重建两个完整容器，验证真实 API 未回归、桌面/移动显示、交互反馈、可访问性和用户文案。
- 资产和实现必须项目自有或许可证兼容；只借鉴设计语言和信息组织，不复制 iKuai 代码、图片、商标或逐像素页面。
- 所有字体、图标和运行资源必须离线可用。

验收：每个页面均有需求、定向源码修改、双产品完整容器、桌面/移动自动 QA 和产品经理明确确认；未确认页面不得标记完成。

### U2：VPP/后端/API 功能拓展探索与实施（P1）

- U1 验收后盘点 stock VPP/插件、后端领域模型与事务、产品 API 和已有容器证据，区分底层可用、后端已接、API 已开和产品已验证。
- 候选功能按用户价值、产品边界、高性能路径、安全闭环、容器可测性和 UI 可表达性筛选；不因为底层存在某项命令就直接增加页面。
- 首批探索二层服务链、链路/节点健康、VLAN、IPv6 完整性、流量可观测性、高可用/配置安全和体验控制；每项先提交能力与缺口报告，由产品经理确认后开发。
- 已批准功能完成模型、API、事务、数据面、回读、回滚、恢复、前端和完整容器验证后才算实现。

验收：每个新增功能均有用户价值和边界确认、VPP/后端/API 现状证明、完整实现、真实包流/故障/性能和浏览器证据；未获产品经理批准的探索项不进入生产固件。

### R1：双产品安装、升级与 ARM64（P1）

- 完成 Gateway/Orchestrator 的 x86_64 与 ARM64 独立产物。
- 验证全新安装、同产品升级、失败回滚和卸载；禁止跨产品原地转换。
- 产物包含离线 Web 资源、服务、配置 schema、迁移和校验清单。

验收：四种产品/架构组合均通过干净系统安装与升级测试，产物清单和哈希可追踪。

- 固化发布说明、已知限制、升级/回滚步骤和验收证据索引。

验收：每种目标硬件有签名测试报告；发布包可由提交、依赖锁和构建日志复现。

## 6. 全局完成定义

产品只有同时满足以下条件才可标记完成：

- 功能、API、持久化、运行时和 UI 形成真实闭环。
- 自动化契约、集成、浏览器、系统产物和[双产品全功能验收设计](container-network-validation.md)全部通过；DNS/DHCP、路由/NAT、容器 PPPoE、WAN/代理、满载 QoS、安全/遥测、服务链 bypass 及故障注入任一缺失时不得宣布全功能验收合格。
- x86_64/ARM64 的安装、升级和回滚证据完整。
- 产品边界测试证明两个产物没有越界服务、资源和页面。
- 数据面选择证明确认原生优先、DPDK 受控回退、整机最高共同合格等级、无兼容性降级，并且管理口永不被接管。
- 两产品全部页面使用同一项目设计系统，并通过交互、响应式、可访问性和视觉回归验收。
- 地址/端口等策略条件使用类型化表达，支持适用的 `any`、CIDR、连续范围和对象引用，且接口地址与产品边界不被混淆。
- 文档与当前提交一致，不使用未验证能力或未来计划描述现状。
- 所有外部阻塞已解除，发布构建由受控 CI 生成并可复现。
