# LY-Route 双产品 UI 优化与功能拓展计划

本计划分为两个连续阶段：

1. **显示效果与交互优化**：从登录页开始，Gateway 和 Orchestrator 对应页面同时进入 QA。产品经理逐项提出修改要求，只修改明确指定的内容；当前页面通过产品经理容器验收后才进入下一页面。
2. **功能拓展**：第一阶段验收后，再基于当前 VPP、后端和 API 的真实能力探索有用户价值的新功能，逐项评估、设计、实现和验证。

## 1. 第一阶段：双产品显示效果与交互优化

### 1.1 页面验收制

- 固定从 Gateway 与 Orchestrator 的登录页开始。两产品同类页面保持统一风格，只保留产品名称和必要内容差异。
- 每次只处理产品经理当前指定的页面和修改点。未被提出的颜色、布局、字段、文案或交互不得擅自改变。
- 通用 CSS/组件的修改必须限制影响范围；如会改变其他页面，修改前明确说明影响，不以“统一设计”为理由连带重构。
- 当前页面未得到产品经理明确验收前，不进入下一页面，不启动功能拓展，也不构建生产固件。
- 本阶段不增加后端字段、不改变 API 契约、不改变业务规则，不使用 fixture、mock 或伪造数据改善画面。

### 1.2 单页 QA 与修改循环

1. **现状 QA**：检查当前页面的桌面/移动截图、DOM、CSS、交互、键盘、错误提示和真实 API 行为，只报告事实。
2. **产品需求**：产品经理明确提出要修改的内容；前端专家确认理解和影响范围。
3. **定向修改**：只修改被确认的页面源码及必要的局部样式，不顺手重构其他页面。
4. **完整容器**：重建 Gateway 与 Orchestrator 完整前后端容器，保留多虚拟网口拓扑，不使用静态演示页代替。
5. **自动 QA**：验证桌面/移动布局、登录成功/失败、键盘焦点、浏览器异常、目标文案和未授权访问。
6. **产品验收**：提供容器地址和截图，等待产品经理确认。未通过则继续当前页面；明确通过后再由产品经理指定下一页面。

### 1.3 当前页面：登录页

当前工作范围固定为：

- Gateway 登录页。
- Orchestrator 登录页。
- 两页共同的登录组件和响应式样式。
- 登录提交、错误反馈、密码输入、键盘和移动端可用性回归。

应用内侧栏、顶部栏、概览、表格、表单和业务页面暂不修改。登录页的具体视觉和交互变化以产品经理接下来提出的要求为准。

### 1.4 页面 QA 基线

- 交互可参考 Panabit 的成熟配置产品，视觉可参考 iKuai 4.0 的浅蓝白，但具体采用哪些元素由产品经理逐项确认。
- 页面不能出现开发语义、内部英文状态、实现组件名或伪造状态。
- 不允许原生控件裸露、文字遮挡、布局溢出、不可见焦点或移动端无法操作。
- 两产品风格一致，产品名称和能力边界清晰，不复制第三方代码、商标、图片或逐像素布局。

### 1.5 页面完成记录

每个通过页面记录：产品需求、修改文件、影响范围、容器地址、桌面/移动截图、自动 QA、遗留问题和产品经理验收结论。自动测试通过不能替代产品经理验收。

### 1.6 Gateway 系统概况 WAN 趋势约束

- 系统概况中的 WAN 流量趋势只按逻辑出口绘制，必须覆盖单 WAN、WAN 组和代理 WAN；颜色仅用于区分出口，不按 DPI、协议或应用分类。
- 每个采样点的出口值定义为该出口上行速率与下行速率之和；图表展示所有逻辑出口的堆叠总和，不拆分上下行曲线。
- 图表纵轴下边界固定为 0，峰值、当前值和平均值均基于上述出口上下行总和计算。
- API 接入时，前端必须使用真实流量趋势接口返回的逻辑出口与采样数据；不得使用 fixture、模拟流量或为了填充图表而生成伪数据。
- 前端验收必须验证：单 WAN、WAN 组、代理 WAN 均能进入图例和图层；接口无数据时显示空状态，不改变图表计算口径。

## 2. 第二阶段：基于 VPP、后端和 API 的功能拓展

### 2.1 能力探索方法

第一阶段通过后，建立三层能力台账：

1. **VPP 数据面能力**：当前固件所含 stock VPP 版本、插件、CLI/API、feature arc、L2/L3、ACL/classify、ABF、NAT、QoS、会话、遥测和硬件路径能力。
2. **后端能力**：已有领域模型、编译器、事务、持久化、应用、回读、回滚、恢复、权限和审计能力。
3. **产品 API 能力**：现有公开 API 能否表达配置、查询实时状态和完成完整生命周期。

每项候选必须区分“VPP 能做”“后端已接入”“API 已开放”“容器已验证”“目标硬件已验证”，不能把底层存在误写成产品已支持。

### 2.2 候选功能筛选标准

候选功能只有同时满足以下条件才进入产品设计：

- 解决家庭、办公或安全网关/编排器用户的真实问题，不是为了展示底层技术。
- 符合 Gateway 或 Orchestrator 的产品边界，不把 NAT/DNS/DHCP/代理能力塞入 Orchestrator。
- 能保持 VPP 高性能主数据面，不引入 Linux 慢路径兼容性回退。
- 能形成配置、事务应用、语义回读、回滚、重启恢复和故障诊断闭环。
- 有可执行的容器协议/包流、故障和性能验收方法。
- UI 能用用户语义表达，不要求用户理解 VPP 对象、内部 ID 或命令。

### 2.3 首批探索方向

以下是待核对的方向，不代表已承诺支持：

- **Orchestrator 原生二层基础链路**：使用 stock VPP bridge-domain、xconnect、L2 FIB 和 ACL/classify 建立 WAN/安全设备/LAN 基础链，动态策略导流作为其上层能力。
- **链路与节点健康**：利用接口、邻居、BFD/探测和计数器形成更快的主备、故障 bypass 与恢复判定。
- **VLAN 与逻辑接口**：评估 VLAN 子接口、trunk/access、逻辑 LAN/WAN 和透明编排组的成熟配置价值。
- **IPv6 完整性**：评估 IPv6 路由、ACL、DHCPv6/RA、DNS 接管、NAT/代理边界和服务链对称性缺口。
- **流量可观测性**：评估基于 VPP 接口、ACL/classify、策略命中和会话计数的历史趋势、异常连接和路径可视化。
- **高可用与配置安全**：评估网关冗余、配置差异预检、防失联提交、定时回滚和灾难恢复能力。
- **性能与体验控制**：评估更多硬件队列/RSS、QoS 队列、拥塞状态和满载体验指标，但不暴露底层调优参数给普通用户。

每个方向先输出“用户价值、现有能力、缺口、实现边界、风险、验收方法和建议优先级”，由产品经理确认后再开发。

### 2.4 单功能实施闭环

确认后的功能按以下顺序实施：

1. 产品需求和边界确认。
2. VPP/后端/API 现状证明。
3. 数据模型和 API 契约。
4. 后端事务、数据面应用、回读、回滚和恢复。
5. 前端交互设计与源码实现。
6. 完整容器协议/包流、故障、性能和浏览器验证。
7. 产品经理验收并更新能力台账。

## 3. 最终收口

第一阶段显示与交互验收、第二阶段已批准功能全部闭环后，再执行双产品全功能矩阵、升级回滚、长稳、性能和真机测试。全部证据通过后，才冻结 schema、构建生产固件并执行目标硬件发布验收。
