## 一、产品理解

### 出口网关

网关负责真实上网出口。它包含 LAN/WAN、三种 WAN 组、策略路由、NAT、DNS、DHCP、PPPoE、代理、安全、流量控制、统计和系统维护。代理是依附真实 WAN 的逻辑出口，订阅策略可选固定节点或 ping 延迟优先的最快健康节点；代理不能加入 WAN 组。

网关必须完整接管 LAN 终端的 TCP/UDP 53。终端即使手工填写 `223.5.5.5` 等公共 DNS，也不能绕过网关 DNS 规则。实际解析服务器和出口线路由网关 DNS 策略决定，DNS 固定线路优先于普通策略路由，线路不可用时失败关闭，不能偷偷泄漏到其他 DNS。

QoS 有两层：用户可配置限速，以及内部不可修改参数的 Smart QoS。Smart QoS 目标是在带宽跑满时仍保护交互时延与主机公平，不要求照搬 CAKE/SQM 实现。

### 流量编排器

编排器不是第二套网关。它只负责把 WAN 进入的流量按规则串过外部双臂设备，再从 LAN 发出；回程严格反向。它不提供 NAT、DNS、DHCP、PPPoE、WAN 组、端口映射、域名、代理和 Top 域名。

编排器只有一个逻辑 WAN 和一个逻辑 LAN，可使用物理口或聚合组。两者都配置后，剩余物理口才能两两组成编排组；每组一个接 LAN、一个接 WAN，可命名，不允许聚合。策略组按页面位置决定优先级，组内规则按序号决定优先级，未命中默认到 LAN。节点故障默认 bypass。

编排器保留流量控制、安全控制、IP 管理、用户管理和配置管理。其中流量控制应是编排器自己的可配置限速策略，不能用网关 NAT/DNS 语义替代。

## 二、已经完成并有真实证据的工作

### 网关

- 任意目标 IPv4/IPv6、TCP/UDP 53 的 VPP 透明接管已通过。保留终端身份和原目标 DNS 响应源地址。
- DNS 固定出口优先于普通策略路由、TTL 更新和上游失效不泄漏已有容器证据。
- Kea DHCP、PPPoE PAP/CHAP 与 IPv4/IPv6 协商、NAT44、安全 ACL、WAN 组、用户限速均有真实协议或包流测试。
- 代理订阅固定/最快节点、ping 主排序、节点失效自动切换和失败关闭已通过容器测试。
- 自研 VPP Smart QoS 插件已完成生产资格、打包、运行时激活和精确回读。2 worker 双向测试在 2 Mbps 配置下约为 1.919 Mbps，多流主机与单流主机聚合份额相等，满载最大 ping 约为 33.5 ms 和 38.5 ms。
- VPP 原生安全防护插件已接入安全配置。SYN、UDP、ICMP 和 ICMPv6 可按接口、源/目的前缀和 PPS 阈值进行精确限速；强制模式真实丢弃超额包，告警模式保留业务并记录超额计数。该插件已随 Gateway deb 交付。
- 安全页可通过只读运行时接口查看 VPP 实际规则的匹配、超额、告警和丢弃计数；VPP 不可读时明确显示锁定或降级，不会把保存的配置误报为正在生效。
- LAN/WAN UI 已增加 Smart QoS 下载/上传带宽输入。带宽必须显式配置，配置无效时锁定，不猜测网卡速度。

### 编排器

- 唯一逻辑 LAN/WAN、物理口或 bond、端口占用保护、共享管理 LAN 的模型/API/持久化已接线。
- 严格两物理口编排组、LAN/WAN 方向、命名和 UI 已接线。
- 有序策略组/规则、VPP ACL/ABF 正反向服务链、未命中直达 LAN、故障 bypass、恢复和重启恢复已有真实 VPP 容器证据。
- 流量概况、在线用户、Top 连接和三视口浏览器主流程已有自动化基础。

### 共同平台

- 全部活动数据口采用一个最高共同合格等级。优先 VPP 原生高性能路径，原生不合格时允许 DPDK/VFIO 回退，两者都不合格就锁定转发。
- DPDK 包、能力探测、VFIO 绑定、VPP 启动/读回、重启和失败回滚已实现。
- 管理口支持独占或与 LAN 共享。共享模式下管理 IP/掩码/网关可以配置在 LAN 物理口上，同时 LAN 数据仍经 VPP 转发。
- Linux forwarding、AF_PACKET、generic XDP、nftables TProxy 和 Linux policy routing 不计入生产转发路径。

## 四、验收进度怎么理解

统一容器运行器目前 `24/24` 通过，包含 DNS、DHCP、PPPoE、NAT、ACL、WAN 组、两层 QoS、代理切换，以及编排器产品/策略/负向/共同数据面契约、生产运行时、服务链、bond 策略包流和双产品浏览器流程。

完整发布矩阵目前 `39/45` 场景通过。编排器的产品隔离、IP-only 策略、负向边界、最高共同合格等级、生产运行时、物理/bond 包流和 `o_ui` 均已有独立证据。完整矩阵仍把功能拆成契约、异常、运行时、真实包流、故障、制品和 UI 等不同层，不能用容器子集推导“产品全部完成”。剩余 6 个场景仍是正式工作计划的验收对象。
