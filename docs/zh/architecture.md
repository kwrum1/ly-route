# LY-Route 双产品架构

LY-Route 从同一代码库构建两个相互隔离的设备产品。产品类型在构建/安装时确定，Gateway 与 Orchestrator 不能在运行时互转，也不共享配置数据库。

## 产品边界

| 维度 | 出口网关 Gateway | 流量编排器 Orchestrator |
| --- | --- | --- |
| 定位 | 路由型出口设备 | 透明流量编排设备 |
| 数据接口 | LAN、WAN 与 WAN 组 | 每个编排组严格两个逻辑接口：`lan_facing`、`wan_facing`；端点可为物理口或 bond |
| 管理 | 设备控制面 | 独立 Linux 管理口 |
| 核心行为 | 路由、NAT、DNS/DHCP、代理、流量治理、安全 | 有序策略；`via`、`direct`、`drop`；正向链及精确反向链 |
| 明确排除 | 运行时产品互转 | NAT、DNS/DHCP、代理、Top Domains/域名对象、OAF/DPI/应用识别/上网行为审计、Bridge、云、HA/VRRP |

两个产品可以共享认证、事务、审计、遥测基础、构建和 UI 基础设施，但每个产物必须分别维护服务、API、资源、路由、数据库和迁移白名单。

## 运行时分层

1. **产品 UI 与 API**：校验用户意图，只展示真实状态。
2. **独立持久化**：保存带版本的产品配置和迁移。
3. **事务协调器**：预检、生成候选、应用、校验，然后提交或回滚。
4. **VPP 数据面**：通过自动选择的原生或 DPDK 接入方式执行转发，并输出计数器和健康状态。
5. **对账与遥测**：在变更和重启后比较期望状态与实际状态。

控制面不得把草稿或内存对象报告为已应用状态。数据面部分应用必须回滚，无法安全回滚时锁定数据面并等待修复。

## 数据面路线

每个已分配的数据网卡都必须自动探测并以证据选择接入方式，策略顺序固定为：

1. 探测所有获准的 VPP 原生高性能候选。首批候选为 RDMA DV 和 VPP AF_XDP zero-copy；根据接入证明、实测包速率、时延、丢包、CPU 开销和 NUMA 亲和性，在通过门禁的原生候选中选择最优者。
2. 没有原生候选通过时，探测 VPP DPDK，作为受控的高性能回退。DPDK 必须通过插件/软件包、PCI 所有权、IOMMU/VFIO、hugepage、队列/RSS、NUMA、接入/退出、真实流量和失败回滚门禁。
3. 两个等级都不通过时，Linux 管理面继续可访问，数据面锁定，并对每个网卡报告失败原因。

策略等级高于评分：存在合格原生路径时不得选择 DPDK。AF_XDP copy、Linux 通用 XDP 转发、AF_PACKET、内核 IP 转发和其他兼容性路径永不进入候选集。PCI ID 或驱动匹配只能作为探测提示，最终选择必须有新鲜的运行时证明；重启、驱动/固件变化、网卡更换或拓扑变化后必须重新对账。

两个产品共用同一选择原则，并采用**整机统一的最高共同合格等级**：候选等级必须被当前全部活动数据接口共同支持，才可供该设备选择。Gateway 不得按 WAN 或端口混用等级；Orchestrator 不得按端口或编排组混用等级，bond 的所有成员也必须满足共同等级。个别端口或成员不再合格时，整机事务化重选共同等级；没有共同合格等级时锁定数据面，禁止局部静默降级。

## Gateway DNS 决策优先级

Gateway 在 LAN 入口默认接管 TCP/UDP 53，将请求重定向到本机 SmartDNS。DNS 决策与普通 PBR 相互独立，执行顺序固定为：

1. 接管 DNS 请求，禁止客户端通过手填外部 DNS 绕过；
2. DNS 规则按用户顺序首匹配，决定固定 WAN/上游/代理解析、固定应答或 NODATA；
3. DNS 查询本身按 DNS 选线发送，DNS 捕获与选线优先于普通策略路由和通用代理捕获；
4. 对 DNS 应答关联的目标 IP 建立带 TTL 的选线绑定，TTL 内业务流量继续使用 DNS 线路，即使普通策略路由选择其他出口；
5. TTL 到期或缓存失效后删除绑定，后续流量重新按普通策略路由计算。

未匹配 DNS 规则时返回 `NOERROR/NODATA`，不使用隐式默认上游。已匹配规则的线路/上游/代理不可用时同样失败，不继续尝试低优先级 DNS 规则或普通默认路由。DNS 规则不直接拥有 NAT、普通路由或下一跳字段；DNS 选线通过带 TTL 的运行时绑定影响关联业务流。默认接管仅指 TCP/UDP 53，不隐含 DoH/DoT 解密或 DPI。

## Gateway 出口选择与 QoS

WAN 组首版语义固定为：

- `primary_backup`：按明确优先级选择健康 WAN，主链路恢复后的抢占行为必须确定且可配置；
- `weighted`：仅在健康成员间按配置权重分配新连接；
- `five_tuple`：以源/目的地址、源/目的端口和协议做稳定散列，在成员集合不变时保持连接粘滞。

代理逻辑 WAN 不得成为 WAN 组成员。订阅代理在策略路由中提供 `fixed_node` 和 `fastest_node` 两种选择：前者绑定稳定节点 ID；后者先用协议握手/探测确认代理实际可用，再以滚动 ICMP RTT 为主要排名依据。ICMP 不可用不得被误判为代理失效，但必须显示延迟指标不可用；切换使用窗口统计、容差、连续失败阈值和最短驻留时间，节点失效时立即把新连接切到健康节点，节点恢复后经连续成功门禁再参与排名。默认不强制中断仍健康的既有连接。

QoS 分两层：

1. **策略限速**：用户按接口、地址/对象、用户或策略设置明确上/下行速率，配置可审计、可读回。
2. **内置智能 QoS**：不给用户暴露 qdisc、队列、AQM 等底层参数；内部采用与 CAKE/SQM 同类的整形、公平排队、按流/主机隔离和主动队列管理能力，在上下行跑满时抑制 bufferbloat，保护交互、语音和游戏体验。

CAKE/SQM 是行为与验收参考，不预先强制具体实现。实现不得绕过 VPP 数据面选择策略，也不得为了接入 Linux qdisc 把业务流量降级到普通内核转发。控制面只暴露必要的启用状态、线路带宽来源和效果指标；内部算法参数不可由用户修改。

## Orchestrator 逻辑端点与故障旁路

编排组由两个不同逻辑接口组成。逻辑接口可以直接引用物理口，也可以引用 bond；两个端点及其底层成员不得重叠或跨组复用，不支持 bridge。运行时以逻辑端点表达策略和遥测，以底层成员执行能力探测和共同等级门禁。

节点健康失败默认执行 bypass：事务协调器从正向链移除失效节点并同步生成严格逆序回程链，验证后原子提交；如果没有健康节点，流量按 `direct` 处理。恢复节点必须连续通过协议健康和双向包流门禁后才能重新加入，切换过程不得形成半链、单向链或环路。

## 可重复功能验收拓扑

仓库必须按[双产品全功能验收设计](container-network-validation.md)提供 Linux 容器化验收拓扑和跨层覆盖清单。Gateway 必须逐项覆盖权限、接口/Bond、LAN/WAN、三种 WAN 组、策略路由、NAT、DNS 权威优先级、DHCP、PPPoE、代理、双层 QoS、安全、对象、遥测、事务、配置、固件和 UI；Orchestrator 必须覆盖产品隔离、管理口、逻辑/Bond 端点、编排组、IP 对象、策略、服务链、默认 bypass、遥测、事务、配置/UI/产物。容器测试负责真实协议与功能包流，目标硬件测试继续负责网卡接入、吞吐、开销、温度和驱动发布门禁。

- [sing-box URLTest](https://sing-box.sagernet.org/configuration/outbound/urltest/)：参考周期探测、切换容差和切换后既有连接处理；本项目额外坚持“协议可用性先行、ping 延迟为主”的产品要求。
- [OpenWrt SQM](https://openwrt.org/docs/guide-user/network/traffic-shaping/sqm) 与 [CAKE 手册](https://man7.org/linux/man-pages/man8/tc-cake.8.html)：参考公平排队、AQM、整形、主机/流隔离与链路开销语义；不预设必须走 Linux 内核慢路径。
- [Docker macvlan 文档](https://docs.docker.com/engine/network/drivers/macvlan/)：参考容器直接接入二层网络的测试拓扑及 Linux 平台限制。

## 配置语义

策略字段使用类型化值，不使用含义模糊的自由文本：显式 `any`、主机、CIDR、连续范围和稳定对象引用。Gateway 可在目标策略具有有效域名语义时使用 IP/域名组；Orchestrator 使用 IP 组并维持“不引入域名对象”的边界。接口自身地址只能是主机前缀，不接受 `any`、范围或对象组。详见[配置表达模型](configuration-model.md)。
