> 本文件保留历史验收证据和环境记录，不是当前开发门禁。当前只在明确的功能批次或发布/硬件任务中使用；日常修复按[开发、热修复与验收流程](development-workflow.md)执行。下文旧版“硬门禁”条款均不再自动阻塞热修复。

本文是出口网关的唯一功能验收台账。勾选表示该功能已经在真实 UI 中填写配置、由后端保存并应用，并在独立虚拟客户端上观察到预期网络行为；仅 API 返回、服务运行或页面显示均不能单独勾选。

编排器不在本文范围，编排器将使用单独的服务链验收台账。

## 历史执行规则（仅供追溯）

本节用于防止重复发生已经确认过的低效修复。它是强制执行规则，不是建议。任一前置门禁失败时，必须停止业务验收；不得继续修改产品源码，不得把测试环境故障登记为产品回归，也不得宣布功能通过。

### 1. 唯一版本与现场一致性

- 工作区源码是唯一修复源。编译机只负责从完整同步的当前源码构建，不允许保留或编译旧后端子目录、旧插件源码和来源不明的二进制。
- 每次部署前后必须记录：Git 提交号和工作区状态、`gateway-control` SHA-256、VPP 自研插件 SHA-256、前端资源 SHA-256，以及被测虚拟机上的对应值。任一值不一致，本轮证据无效。
- 热修复必须按“修改工作区源码 -> 定向测试 -> 编译机完整构建 -> 替换当前虚拟机 -> 记录指纹 -> 重跑同一场景”执行。禁止只在虚拟机内修改后不回写源码。
- 全功能验收期间不重建、不重装 ISO。所有缺陷先在当前虚拟机热部署验证；全功能和重启回归均通过后，才把同一组已验证产物固化进 ISO。

### 2. 持久化验收夹具

- PPPoE 服务器、DNS 权威服务器、VLESS 测试节点、DHCPv6-PD 服务、外部端口服务和独立 LAN 客户端初始化脚本必须由 systemd 或等价持久化机制管理。
- 开始业务测试前必须先运行夹具预检，至少验证：服务为 `active`、预期 TCP/UDP 端口已监听、测试地址和路由存在、PPPoE AC 可发现、DNS 能对约定域名给出正向答案、代理节点能完成独立直连测试。
- 夹具预检失败时，结果只能记为“验收环境失败”，不能记为网关 Bug。修复夹具后重复原场景，禁止因此修改产品源码。
- 重启任何测试虚拟机后，必须先重新运行夹具预检；不得凭重启前状态继续验收。
- 每个客户端探针执行前必须按客户端源地址检查实际路由。尤其是 DNS 透明接管目标不能同时配置在夹具本机；`ip route get 目标地址 from 客户端地址` 必须显示经 LAN 网关转发，若命中 `local` 表只能记为 `FIXTURE_FAIL`。
- 代理产品测试前，必须先用独立 Xray 客户端通过同一个 VLESS/VMess/Trojan/SS 节点完成一次目标请求。Xray 26.4 及以上版本的 Freedom 出站默认阻断私网和保留地址；受控验收目标若位于私网，服务端夹具必须用 `finalRules` 只放行该目标 IP、端口和协议。日志出现 `proxy/freedom: blocked target` 时只能记为 `FIXTURE_FAIL`，不得修改网关源码。

### 3. 冻结拓扑与基线

- 当前功能验收拓扑固定为：网关管理网、独立 PPPoE WAN、独立 LAN、持久化服务端和多个独立 LAN 客户端。
- 一轮全量回归期间禁止新增/删除网卡、切换端口组、改变数据面模式、重装系统或复用管理网作为业务 LAN。
- 确需改变拓扑时，必须新建基线编号，并将 PPPoE、LAN/DHCP、NAT、DNS、代理、ACL、QoS 和 IPv6 的旧运行证据全部标记为需复验，不能混用两套拓扑的结果。
- 双 PPPoE WAN 的基线必须使用两个不同的服务端、两个不同的 AC MAC 和两个独立 WAN 端口组。两条会话连接同一 AC 只能覆盖共享上游场景，不能作为家用多 WAN 的主验收依据。
- 双 WAN 通过前，除 UI、会话和客户端结果外，必须核对 `show pppoe session` 中每条会话的 `encap-if-index`，以及其探针 FIB 的 `stacked-on` 物理接口。会话 ID 正确但 `stacked-on` 指向另一条 WAN 时，结果必须记为 `PRODUCT_FAIL`。

### 4. 分层故障定位

“客户端无法上网”不能直接作为 Bug 定位。必须按以下顺序采证，并明确首个失败层：

1. **夹具层**：PPPoE AC、DNS 上游、代理节点和外部测试服务是否独立可用。
2. **链路层**：接口状态、PPPoE 发现/会话、地址、IPv4/IPv6 默认路由是否正确。
3. **控制层**：真实 UI 提交、API 回读、持久配置和应用事务是否一致。
4. **VPP 层**：接口、FIB、ACL/ABF、NAT、QoS、插件及计数器是否与配置一致。
5. **服务层**：SmartDNS、Kea、Xray 和相关适配服务是否监听正确地址并选择正确出口。
6. **客户端层**：独立客户端的 DHCP/RA、DNS、TCP/UDP/ICMP 和回程是否符合预期。

未找到首个失败层前禁止改代码。若报文已进入 Xray 但对端端口未监听，或 DNS 已透明接管但测试权威服务器返回 NXDOMAIN，应先修复夹具，不能修改网关数据面。

### 5. 批量回归而非串行试错

- 固定使用一条批量回归入口，同时检查夹具预检、PPPoE、DHCP、IPv4 NAT、IPv6 PD/RA、TCP/UDP 53 接管、DNS 分流、代理、端口映射、ACL 和 QoS。
- 每项输出独立的 `PASS`、`PRODUCT_FAIL` 或 `FIXTURE_FAIL`，并保存时间戳、配置代次、VPP 计数器前后值和客户端结果。一个失败不得中断其余互不依赖项目的采证。
- 同批结果用于一次登记全部故障，再集中修复；禁止“修一项、重启、再临时搭一套环境测下一项”的循环。
- 修复后必须重跑失败场景和已通过的核心基线，防止旧 Bug 因新改动回归。

### 6. 验收范围不得漂移

- 本轮必须覆盖原始设计中的全部家用网关功能，包括多 WAN、WAN 群组主备/加权/五元组、PPPoE、LAN/DHCP、NAT/全锥 NAT、端口映射、DNS 分流与透明接管、GeoIP/GeoSite、代理、IPv6、ACL、安全、两类 QoS、监控、配置与升级。
- 本轮只验证功能正确性，不测试吞吐、64 字节小包性能、额外硬件矩阵、VMXNET3 原生 DMA/VFIO 或未列入产品设计的能力。
- AF_PACKET 仅是 ESXi 功能验收通道，不得延伸为生产数据面设计，也不得为了它改变物理机“VPP 原生高性能路径优先、DPDK 回退、均不可用则锁定”的边界。

### 7. 产品缺陷闭环

- 只有完成上述分层诊断并证明首个失败点位于产品代码或产品配置生成链，才允许登记产品 Bug。
- 每个产品 Bug 必须同时具备：最小复现场景、修复前证据、源码修改、定向自动化测试、热部署指纹、修复后同场景证据和核心基线回归结果。
- 现场修复、源码、编译机产物和最终 ISO 必须沿同一产物链前进；禁止让旧插件、旧前端或旧控制程序覆盖已经验证的版本。
- 最终重启回归前不得清空当前配置和证据。重启后先验证夹具，再验证网关持久化恢复，避免再次混淆两类故障。

## 本轮复盘锁定规则

以下规则来自本项目已经发生过的实际失误，后续验收和修复必须照此执行，不能以“先试一下”替代：

1. **不允许版本漂移**：源码工作区、编译机、热部署虚拟机、运行快照和 ISO 必须属于同一产物链。现场临时修改如果没有回写源码、重新构建并核对 SHA-256，一律视为无效修复；旧控制程序、旧前端或旧 VPP 插件不得留在部署目录中参与运行。
2. **不允许把重启后的夹具缺失当成产品回归**：PPPoE、DNS、代理、DHCPv6-PD、外部端口服务和客户端网络必须有持久化启动单元。任何测试虚拟机重启后，先做夹具预检和端口/路由检查，夹具不完整时只记录 `FIXTURE_FAIL`。
3. **不允许混用验收拓扑**：增加/删除网卡、改变端口组、修改 LAN/WAN 地址、切换 AF_PACKET/VPP/DPDK、重装系统都会产生新的基线。旧基线的通过结果不能直接沿用。
4. **不允许清空现场后继续推理**：失败现场、数据库配置、VPP 运行态、服务日志、客户端结果和计数器必须先归档再修复。除非验收计划明确要求，不得初始化数据库、删除策略、重建虚拟机或清除夹具来“恢复干净状态”。
5. **不允许串行盲修**：每轮先批量收集所有独立功能结果，再集中修复；修复后至少重跑失败项和 PPPoE/LAN/DHCP/NAT/DNS/代理核心基线。不得每修一项就重启、重搭夹具、重新调查全环境。
6. **不允许用“客户端不能上网”作为根因**：必须按夹具、链路/会话、控制面、VPP、服务、客户端六层顺序定位首个失败点。没有首个失败层、请求/响应证据和运行态读回，不得改产品代码。
7. **不允许把 API 或 systemd 健康当成业务通过**：真实 UI 配置、后端最终保存、运行时事务提交、VPP/服务读回和独立客户端真实报文必须同时存在。控制服务重启后可能仍显示上一次事务的状态，必须重新执行一次应用并核对新事务 ID，不能把旧读回当作本轮结果。
8. **QoS 必须做命中对照**：TCP 写入端的字节数不是数据面实际吞吐证明。限速验收必须同时记录匹配端口和未匹配端口、VPP policer `conform/exceed/violate` 前后计数、ACL 命中和客户端结果；没有计数器增量或对照组，不得因为一个传输数字勾选 QoS。
9. **不允许验收范围漂移**：本轮只验证原始家用网关设计功能。性能、64 字节小包、额外硬件矩阵、ESXi VMXNET3 原生 DMA/VFIO 和未设计能力另立任务，不得阻塞当前功能验收，也不得因为这些调查改动生产路径。
10. **编排器与网关完全分开**：编排器不参与网关 NAT、DHCP、DNS、PPPoE、代理和网关 QoS 的通过判定；两套前后端、运行态和证据目录不得交叉使用。
11. **全量策略重放必须先清理完整并集**：重建路由策略前，待删除集合必须是“上一快照策略、显式删除策略、当前期望策略 ID”的并集。禁止只依赖可能不完整的上一快照，否则同 ID 的旧 ACL/ABF 会阻塞新策略附着。
12. **运行态读回必须区分实现路径**：普通策略从 ACL/ABF 读回；大规模 GeoIP 策略从 pre-NAT Radix/LPM 分类器和对应 FIB 下一跳读回，并核对启用状态、LAN 前缀、优先级、规则数、表 ID、NAT bypass。Radix 策略没有 ACL/ABF 不是失败。
13. **大规则集重放必须有固定批处理和幂等门禁**：VPP 命令默认每批 `512` 条，禁止恢复遗留 ESXi 专用的 `32` 条分批。修改策略生命周期、快照解码或批处理后，必须连续提交两次完全相同的真实 UI 配置；两次均为 `committed/running`，服务健康且独立客户端核心报文通过，才允许关闭缺陷。
14. **DHCP 控制流量不得进入用户分流策略**：每次生成 pre-NAT 策略时必须先安装优先级为 `0` 的 UDP `68 -> 67` 绕过规则，覆盖 Discover、Request 和 Renew。每次真实 UI 应用后，批量验收必须让独立 LAN 客户端重新取得租约；仅 Kea 运行、API 成功或 VPP 中存在 ABF 规则都不能判定 DHCP 通过。
15. **代理节点必须先独立验活**：批量验收的 `LY_ROUTE_PROBE_PROXY_NODE_FIXTURE` 必须先通过，随后才判断网关的直连/代理策略。该预检必须穿过实际节点协议并取得目标服务响应，仅端口可连接或 Xray 打印 `accepted` 不算通过。私网目标必须配置最小范围的 Freedom `finalRules allow`，不得全局关闭节点安全边界。
16. **GeoIP 大表与普通配置事务分层判定**：GeoIP 前缀不得展开为海量 ACL。验收先核对 pre-NAT Radix/LPM 分类器的规则数、节点数和目标 FIB，再发客户端流量检查命中计数；代理节点或 DNS 上游失败不得回退成“GeoIP 加载失败”。同一 GeoIP 内容未变化时，普通 DHCP、QoS、用户或遥测配置修改不得作为重新导入大表的通过条件。

### 结果分类和停机条件

批量回归只允许输出四种结果：

| 结果 | 含义 | 后续动作 |
| --- | --- | --- |
| `PASS` | 四层证据齐全且客户端行为符合预期 | 记录证据并保留现场 |
| `PRODUCT_FAIL` | 首个失败点在产品源码、配置生成或运行时应用链 | 登记最小复现并修复 |
| `FIXTURE_FAIL` | PPPoE/DNS/代理/服务端/客户端夹具不满足前置条件 | 只修夹具，重跑原场景 |
| `BLOCKED` | 外部网络、硬件或权限使本轮无法取得证据 | 保留现场，不得宣称通过 |

出现 `FIXTURE_FAIL` 或 `BLOCKED` 时，停止对应业务结论；出现 `PRODUCT_FAIL` 时，先保存证据再编辑源码。任何未分类的失败都不能进入下一阶段。

## 证据标准

每一个勾选项必须同时具备以下证据：

1. **UI**：以管理员身份在控制台创建或修改配置并回读。
2. **控制面**：API 和服务端保存的配置与 UI 一致，重启相关服务后仍可读取。
3. **数据面**：VPP/代理/DNS/DHCP 等实际运行状态与配置一致。
4. **客户端**：独立 LAN 客户端通过真实报文得到预期结果。
5. **恢复性**：涉及持久配置的项目重启后再次验证。

## 虚拟机与物理机判定边界

- ESXi + VMXNET3 + AF_PACKET 只用于验证 UI、控制面和数据面功能闭环，不作为生产性能或网卡独占能力的通过证据。
- 物理机必须独立验证网卡驱动识别、PCI/VFIO 所有权切换、VPP 原生高性能路径、DPDK 回退、重启恢复及链路故障恢复；虚拟机结果不得代替这些勾选项。
- 修复不得为 VMXNET3 改变物理网卡的默认选择顺序。物理机仍按“VPP 原生高性能路径优先、DPDK 回退、均不可用则锁定”的产品边界执行。
- 涉及接口枚举、重命名、能力探测或所有权切换的修复，必须同时覆盖现有 VPP 接口不被误删、管理口不被接管、物理 PCI 身份稳定三个回归条件。

### 修复的跨环境门禁

每个数据面修复先判断它属于“通用控制面/数据面逻辑”还是“VM 兼容适配”。
VM 兼容适配只能增加验收能力，不能改变物理机的生产选择顺序，也不能把
VMXNET3、AF_PACKET 的低性能路径写成物理机能力。涉及网卡的改动必须在真实
硬件上重新检查以下项目，未取得证据不得勾选：

| 状态 | 真机回归项 | 必须保留的证据 |
| --- | --- | --- |
| [ ] | 驱动与 PCI 识别 | `lspci -nnk`、驱动名、MAC、PCI 地址 |
| [ ] | 管理口排除 | 管理口仍由 Linux 配置，未出现在 VPP/DPDK 数据口清单 |
| [ ] | 数据口所有权 | VPP 原生或 DPDK 绑定前后驱动、PCI 所有权和 VPP 硬件接口 |
| [ ] | 多口一致性 | 所有选定数据口使用同一合格等级，不能一口 native、一口不明路径 |
| [ ] | 不可用时锁定 | native 与 DPDK 均不满足时不启动半成品数据面，并记录原因 |
| [ ] | 重启与链路恢复 | 重启、拔插/链路 down-up 后 MAC/PCI 映射和所有权不漂移 |

因此，ESXi 上修复通过只代表功能场景可以继续验收；物理机的驱动、DMA、
IOMMU/VFIO、队列和所有权结果必须单独登记，不能由虚拟机结果推断。

## 运行态应用与证据边界

- 生产运行态应用使用类型化 VPP 事务；必须先完成目标图的 VPP 读回，再将事务标记为提交。
- `/var/lib/ly-route/vpp/operations.json` 只作为重启恢复配置保存。`vpp-apply-receipt.json` 只属于启动恢复脚本，不能作为类型化运行事务的收据。
- 运行态通过条件为：同一事务提交、类型化网关证据完整、VPP 实时读回成功、已配置服务健康。旧的恢复收据过期不等于产品故障。
- 任何失败必须先保留首个事务、日志和读回证据，分类为 `PRODUCT_FAIL` 或 `FIXTURE_FAIL` 后再处理；禁止未分类就重复全量验收。
