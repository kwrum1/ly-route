# 开发、热修复与验收流程

> 当前有效流程：2026-08-18。本文是开发流程的唯一入口。
>
> 产品功能边界、架构和 UI 规范仍然有效；旧文档中的“每次修改都必须全量验收”、纯代码行数限制、ESXi/VMXNET3 硬件门禁和 ISO 重装门禁已经废止，不得再阻塞日常修复。

## 目标

让一次修复在最短时间内形成可追踪闭环，同时不丢失真正有价值的证据：

`复现 -> 找到首个失败层 -> 修改源码 -> 定向检查 -> 热部署 -> 同场景复测`

只有功能批次收口或发布时，才进入全量功能验收和 ISO 构建。日常修复不重建 rootfs，不重装 ISO，不做性能测试，不等待物理硬件。

## 三种工作模式

### 1. 日常开发与热修复（默认）

适用于一个 Bug、一个页面、一个 API、一个服务或一个 VPP 插件的修改。

1. 在当前环境复现一次，并记录最小证据：命令、日志中的首个错误或客户端现象。
2. 先分类首个失败层：测试夹具、链路/会话、控制面、VPP/服务、客户端。夹具失败不修改产品源码。
3. 只修改当前完整源码树，运行 `bash scripts/dev-hotfix-check.sh`；能确定包范围时传入 Go 包路径。
4. 在固定编译环境仅构建受影响的二进制或插件。Go 服务使用 `scripts/build-hotfix-go.sh`；其他文件构建后必须使用 `scripts/seal-hotfix-artifact.sh` 封装。产物进入按源码指纹隔离的 `dist/hotfix/`，不构建 rootfs/ISO。
5. 使用 `scripts/hotfix-deploy.sh --manifest ...` 替换目标文件。脚本从清单定位产物，并在部署前同时核对当前源码指纹和 SHA-256；任何旧产物或构建后又改过源码的情况都会被拒绝。
6. 从原来的 UI/API/客户端场景复测；通过后记录修复指纹和结果。

热修复的完成条件只有两个：原场景通过，且核心冒烟仍通过（管理面可访问、VPP/相关服务可查询、一个适用的基础转发或编排路径可用）。

### 2. 功能验收批次

当一个产品功能批次准备交付时执行一次，不随每个小修复重复执行。

- Gateway：使用现有批量入口 `scripts/test-gateway-live-batch-acceptance.sh` 或对应容器批次脚本，一次收集 PPPoE、LAN/DHCP、NAT、多 WAN、DNS、代理、QoS、安全和遥测的结果。
- Orchestrator：只验证接口编排、服务链、策略组/明细、顺序、匹配和 bypass；不重复验收 Gateway 的 NAT、DHCP、DNS、PPPoE。
- 每项结果标为 `PASS`、`PRODUCT_FAIL`、`FIXTURE_FAIL` 或 `BLOCKED`。一次批次先收集全部独立失败，再集中修复。
- 只有改动影响某个已通过核心路径时，才重跑核心冒烟；不因为一个文案或单元测试改动重建整套环境。

功能验收仍遵守四个证据点：真实 UI 配置、后端持久化、运行态应用、独立客户端报文。四点是功能批次的通过条件，不是每次源码改动的门禁。

### 3. 发布构建

只有功能批次通过后执行：

1. 用固定的 Bookworm/Go/VPP 工具链从当前源码构建运行包。
2. 构建 rootfs、磁盘镜像、ISO 或 ARM 安装包及升级包。
3. 校验架构、依赖、插件清单、SHA-256 和安装启动冒烟。
4. 发布产物只来自这一次构建；旧产物不能作为证据。

发布构建是发布门禁，不是热修复门禁。ISO 安装、物理 PCI/VFIO、性能和温度测试只在明确的发布/硬件任务中执行。

## 最小门禁

日常流程只保留以下四个门禁：

| 编号 | 门禁 | 适用时机 | 通过标准 |
| --- | --- | --- | --- |
| G1 | 源码门禁 | 每次修改 | `git diff --check`（排除 patch 文件的嵌入式 diff 标记）、脚本语法检查、受影响 Go 包编译通过 |
| G2 | 产物身份 | 每次热部署 | 目标文件 SHA-256 与构建输出一致，旧文件有备份 |
| G3 | 功能冒烟 | 每次行为修复 | 原场景通过，受影响服务/数据面状态可查询 |
| G4 | 发布门禁 | 功能批次收口/发布 | 批次验收通过，产物链和安装冒烟通过 |

G1-G3 之外的检查只能作为证据或诊断，不得自动升级成阻塞门禁。门禁失败时报告具体失败层，不用“客户端不能上网”作为泛化结论。

## 结果分类

- `PASS`：产品行为已按当前任务验证。
- `PRODUCT_FAIL`：首个失败点在源码、配置生成或产品运行时。
- `FIXTURE_FAIL`：PPPoE 服务器、代理节点、DNS 权威、客户端或网络拓扑不可用；先修夹具，不改产品。
- `BLOCKED`：缺少外部资源或权限，尚未形成产品结论；不计入通过，也不要求反复重跑。

## 明确废止的旧门禁

以下项目不再进入日常 `ci-verify.sh`，也不能阻塞热修复：

- 纯 LOC/文件长度限制；代码质量通过编译、测试和评审判断，不用固定行数阻断构建。
- 每次修改都执行 rootfs、ISO、完整后端测试和全部历史 `.sisyphus` 契约。
- 每次验收前清空并重建 VM、PPPoE 服务器和客户端；默认保留现场并复用拓扑。
- ESXi、VMXNET3、VFIO、IOMMU、性能、64 字节包和真实物理硬件门禁；它们只属于单独的硬件/发布任务。
- 将编译机环境检查、换行规范化、下载依赖和 ISO 安装当成每次代码修复的前置条件。编译环境检查只在发布构建或明确的构建排障任务执行。
- 旧 VPP 子目录、旧 rootfs、旧 deb、旧 ISO 和旧串口日志参与当前结论。它们只能作为历史证据，不能混入当前产物链。

废止门禁不等于删除产品需求。Gateway 原设计功能和 Orchestrator 原设计功能仍是功能批次的验收范围，只是按批次验收，而不是每次改动重复验收。

## 固定入口

```bash
# 日常修复：只做最小源码门禁
bash scripts/ci-verify.sh

# 只检查受影响包
bash scripts/dev-hotfix-check.sh ./internal/runtime/vpp ./internal/httpapi

# 构建带源码指纹的网关控制服务热修复产物
bash scripts/build-hotfix-go.sh --package ./cmd/gateway-control --name ly-route-control

# 清理白名单中的本地产物（默认不执行删除，增加 --apply 才删除）
bash scripts/clean-generated.sh

# 功能批次：一次收集结果
./scripts/test-gateway-live-batch-acceptance.sh

# 发布前：完整产物与安装链
./scripts/ci-release-verify.sh
```

任何新门禁必须说明：它防止的具体故障、适用阶段、替代的旧检查，以及移除条件。没有这四项说明，不得加入日常入口。

## 上下文与文档读取边界

日常任务只先读取仓库根目录 `AGENTS.md` 和目标源码。只有任务涉及对应领域时，才打开该文档：产品边界、UI、ISO、硬件或架构。不得在每次恢复任务时顺序读取 `docs/`、历史验收账本或归档目录；应先搜索具体功能名、错误信息或文件路径，再读取命中的小段内容。长验收结果只保留结构化结论和当前失败项，不反复加载完整日志。
